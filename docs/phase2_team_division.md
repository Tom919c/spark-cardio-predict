# 第二阶段小组分工与协作边界

## 1. 分工目标

阶段二采用“一个负责人、一个文件边界、一个交付结果”的方式协作。每名成员可以和其他成员联调，但不能同时修改同一批核心文件，也不能把未完成的业务逻辑直接推给组长重构。

`chenquan` 是集成开发分支，`main` 只接收完成验收的正式版本。所有成员先在自己的开发分支工作，完成后提交到 `chenquan`，通过集成测试后再发布到 `main`。

## 2. 五人职责总览

| 角色 | 主责方向 | 主要交付 |
| --- | --- | --- |
| 组长 | 总体架构、接口契约、后端集成和最终验收 | 阶段二接口文档、集成代码、跨模块测试、发布清单 |
| 成员一 | 上传后端、任务管理、DAO、知识规则和隐私校验 | 分片上传、SQLite/MySQL DAO、任务状态、规则知识库、后端测试 |
| 成员二 | 数据工程、HDFS/Spark、区域分析和快照指标 | Spark 作业、区域聚合、ADS 输出、快照结果和数据样例 |
| 成员三 | 机器学习和模型服务 | What-if、批量预测、SHAP、模型评估、Stacking 候选报告 |
| 成员四 | 前端页面、动态地图和交互测试 | 上传页面、任务轮询、动态地图、快照折线图、离线资源和浏览器测试 |

## 3. 组长职责和边界

### 负责内容

- 阅读并维护 `docs/phase2_task_plan.md`、`docs/api_design.md` 和相关协作规范。
- 确定上传协议、任务状态、结果 JSON 和错误码，先提供样例再允许开发。
- 负责 Flask 路由注册、跨服务编排和集成测试。
- 审查模型版本、数据版本、HDFS 输出路径和成员提交内容。
- 维护 `chenquan` 集成分支，安排联调、回归测试和正式发布。
- 确认模型指标、隐私策略和医学文案没有越过项目边界。

### 文件边界

- `docs/` 中的阶段二任务、接口和集成说明。
- `src/controllers/__init__.py` 及跨模块路由注册。
- `tests/` 中的集成测试和 API 契约测试。
- `config/` 的共享配置只允许由组长最终合并，其他成员通过提交配置变更说明提供修改建议。

### 不负责的内容

- 不直接重写成员的 Spark 作业、模型算法或前端页面。
- 不在没有评估报告的情况下替换 active 模型。
- 不在本地手工修改任务状态或绕过接口测试来“修复”联调问题。

### 交付结果

- 一份固定的接口契约和错误码清单。
- 一套可以运行的集成测试。
- 每个里程碑的合并记录、测试结果和剩余风险。
- 阶段二发布前的版本验收清单。

## 4. 成员一：上传后端、任务、DAO 与知识规则

### 负责内容

- 分片上传初始化、分片接收、断点续传、哈希校验和完成合并。
- `datasets`、`tasks`、必要的 `upload_sessions` 元数据表。
- SQLite 与 MySQL 的 `get_db_conn()` 切换和原生 SQL DAO。
- HDFS 上传、临时路径清理和结果路径登记。
- 后台任务状态持久化，状态包括排队、运行、成功、失败和取消。
- 本地 JSON 规则知识库和规则检索服务。
- 文件大小、扩展名、文件名、预览行数和敏感字段校验。

### 文件边界

- `src/dao/` 中新增或修改的数据库、HDFS DAO。
- `src/controllers/upload_controller.py`、`src/controllers/task_controller.py`。
- `src/services/upload_service.py`、`src/services/task_service.py`、`src/services/knowledge_service.py`。
- `resources/knowledge/intervention_rules.json`。
- 数据库初始化和迁移脚本。

不得直接修改 `src/ml/`、`src/spark_jobs/` 和前端模板。需要新增配置时提交配置清单，由组长统一合并。

### 交付结果

- 分片上传接口和请求样例。
- SQLite 建表脚本以及 MySQL 兼容说明。
- HDFS 路径和任务状态流转说明。
- JSON 知识库示例、规则优先级和回退模板。
- 上传、重复分片、哈希错误、数据库错误和任务失败测试。

## 5. 成员二：数据工程、HDFS/Spark、区域和快照

### 负责内容

- 上传数据的字段标准化和区域层级识别。
- 成都区县、社区和多城市数据的聚合逻辑。
- Spark 清洗、质量统计、区域风险聚合和 ADS 输出。
- 批次 `data_period` 处理、快照指标生成和多批次比较数据准备。
- HDFS raw、feature 和 ADS 目录结构的实现与重复执行策略。
- 确保 Spark 结果字段稳定，供 Flask 和前端消费。

### 文件边界

- `src/spark_jobs/` 中的 ETL、聚合、快照相关作业。
- `src/services/region_service.py`、`src/services/snapshot_service.py`。
- Spark 输出 schema、样例数据和 Linux 运行说明。

不得在 Spark 作业中修改模型训练参数、模型清单或 Flask 请求逻辑。不得使用无边界的 `toPandas()` 处理 200 万行原始数据。

### 交付结果

- Spark 作业启动命令、输入字段和输出字段说明。
- `quality_report`、`region_summary`、`snapshot_summary` 等 ADS 样例。
- 成都区县、单区县社区和无区域字段三类测试数据。
- HDFS 链路的成功、失败、重跑和输出目录已存在测试。
- 快照指标可以被前端直接绘制，不需要前端重新计算风险率。

## 6. 成员三：机器学习和模型服务

### 负责内容

- 保持心脏和卒中两个独立模型，不改变目标标签和阶段一特征契约。
- What-if 基线/情景预测服务。
- 批量双模型评分和分块预测。
- SHAP 模型缓存、解释器缓存、输出格式和异常降级。
- Logistic、Random Forest、GBDT/HistGradientBoosting 的离线比较。
- 每个目标独立的 Stacking 候选实验，不直接发布。
- 风险阈值、概率校准、PR-AUC、Recall、F2 和 Brier Score 分析。

### 文件边界

- `src/ml/` 中的 What-if、批量预测、解释器、评估器和候选模型代码。
- `src/services/what_if_service.py`、`src/services/batch_risk_service.py`，如确需新增服务。
- 模型实验报告和测试数据，不提交模型二进制文件。

不得修改前端模板、上传协议和 Spark 输出字段。需要变更模型接口时，必须先提交接口变更说明并由组长确认。

### 交付结果

- What-if API 的请求、响应和边界条件。
- 批量评估的字段映射、失败行处理和结果格式。
- SHAP 可用、不可用、模型损坏三类测试。
- 模型比较报告和候选 Stacking 报告。
- 明确的模型发布建议：保持现模型、替换模型或暂不发布。

## 7. 成员四：前端、地图和浏览器验证

### 负责内容

- 分片上传、进度显示、断点续传和失败重试。
- 任务状态轮询 `/api/task/status/<task_id>`。
- 根据 `coverage_level` 和 `map_available` 动态选择地图、排名表或柱状图。
- 成都区县地图、单区县社区排名和多批次快照折线图。
- C 端 What-if 交互和基线/情景结果展示。
- 本地 ECharts、Bootstrap、词云插件和 GeoJSON 资源加载。
- 空数据、失败、断网、模型未就绪和数据处理中状态。

### 文件边界

- `templates/`。
- `static/css/`、`static/js/`、`static/echarts/`、`static/geo/`。
- 浏览器端测试和页面截图记录。

不得在前端硬编码全国地图、四川省单点或风险计算公式。页面只能使用后端返回的指标和元数据。

### 交付结果

- 上传和任务状态页面。
- 动态区域展示的三类验收截图。
- 快照折线图和 What-if 结果页面。
- 无网络环境下的页面演示结果。
- 浏览器测试报告和页面异常状态说明。

## 8. 跨成员依赖关系

| 前置交付 | 使用者 | 约束 |
| --- | --- | --- |
| 上传和任务 JSON 契约 | 后端、前端、组长 | 契约冻结后才能并行开发 |
| ADS 输出 schema | 数据成员、后端、前端 | 字段名和单位不能由前端自行修改 |
| 模型评分接口 | ML、Spark、后端 | 必须包含模型版本和特征版本 |
| 区域元数据 | 数据成员、前端 | 前端不自行推断地图层级 |
| 规则知识库 schema | 后端、前端、组长 | 每条建议必须有来源和版本 |
| 本地地图资源 | 数据成员、前端 | 资源必须可离线加载并注明许可证 |

如果一个成员需要修改其他成员负责的文件，必须先在 `chenquan` 分支提交说明，获得文件负责人和组长确认后再修改。

## 9. 里程碑安排

### M0：契约冻结

- 确认上传协议、数据库表、任务状态、ADS 输出 schema 和错误码。
- 五名成员各自提交一份输入、输出、依赖和测试清单。

### M1：后端和数据链路

- 分片上传和元数据库可以独立测试。
- HDFS raw 和 Spark ADS 可以用测试数据跑通。
- 没有前端时可以使用 API 或脚本查询任务状态。

### M2：机构端页面

- 成都全区县显示区县地图。
- 单区县显示社区排名。
- 上传、任务轮询、错误提示和结果展示闭环跑通。

### M3：C 端和模型增强

- What-if、批量评分和 SHAP 优化完成。
- 模型候选比较报告完成，未审核候选不能成为 active 模型。

### M4：规则、隐私和离线验收

- 本地 JSON 知识库接入固定模板。
- 小样本匿名化和敏感字段掩码通过测试。
- 断网时页面和核心演示可用。

### M5：发布验收

- 完整测试通过。
- 组长检查接口、文档、配置和 Git 差异。
- 先合并 `chenquan`，再由组长审核发布到 `main`。

## 10. 统一提交和交付规则

每个成员的提交必须包含：

- 修改文件和未修改文件说明。
- 接口或数据字段变化。
- 测试命令及结果。
- 是否依赖本地数据、HDFS、Spark、Redis 或 MySQL。
- 失败场景和剩余风险。

每个功能分支只完成一个主题，例如 `phase2-upload-chunk`、`phase2-spark-snapshot`、`phase2-what-if`。禁止把格式化、无关重构、模型训练产物和个人配置混入提交。

提交前必须检查：

1. 没有个人绝对路径、个人环境名、密钥和真实居民数据。
2. 没有模型二进制文件、SQLite 数据库、日志和临时上传文件。
3. 新增接口有失败和空数据测试。
4. 文档字段与代码字段一致。
5. 代码已在对应的本地或 Linux 环境完成最小验证。

## 11. 需要提前确认的风险

- HDFS 分片合并、Spark 执行节点读取模型和 Windows/Linux 路径是本阶段的最高技术风险，应在 M1 先做最小链路验证。
- 后台线程不能依赖 Flask 请求上下文；每个线程必须单独管理数据库连接。
- Flask 调试重载可能启动重复线程，开发启动方式必须避免重复提交 Spark 任务。
- Spark 任务失败后必须写入失败状态，不能让前端永久停留在“运行中”。
- 社区小样本保护必须同时作用于地图、统计图、导出文件和随访名单。
- 快照数据的区域口径和模型版本不一致时，前端应拒绝合并绘图。
- 医疗知识库内容需要组内审核、来源记录和版本控制，不能由模型或前端临时生成。
- `main` 只接受完成测试和风险说明的集成提交。
