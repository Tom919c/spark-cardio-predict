# 第二阶段任务与技术方案

## 1. 文档定位

本文档是第二阶段的统一任务清单和技术约束。它把已经确认的算法、数据流、机构端功能、C 端功能、联网边界和验收标准集中在一起，作为组员开发和组长集成时的共同依据。

第二阶段的目标不是推翻阶段一，而是在阶段一双模型可运行的基础上，完成机构端数据接入、区域分析、快照对比、个人情景模拟和系统工程化增强。

## 2. 已锁定的设计决策

### 2.1 算法模型

- 保留两个独立的二分类模型。
- 模型 A 预测 `label_heart`，模型 B 预测 `label_stroke`。
- 两个模型分别使用随机森林和保序回归校准，不能改成互斥多分类模型。
- 上传数据只用于分析和批量评估，不自动覆盖正式模型，也不自动触发重新训练。
- 每次个人预测、批量评估和机构分析都必须记录模型版本、特征版本和数据集编号。
- 阶段二中的概率是模型输出，不代表临床诊断，也不能直接解释为干预后的因果结果。
- 卒中不平衡处理继续只作用于训练子集，校准集和测试集保持自然患病率；不得用合成病例或过采样测试集虚增效果。

### 2.2 大文件处理

- 前端使用 JavaScript 分片上传，后端支持分片乱序、重复上传和断点续传。
- 官方大文件链路为：分片上传 -> HDFS raw 临时目录 -> 合并为 HDFS 原始文件 -> 后台线程提交 Spark 作业 -> ADS 结果写入 HDFS。
- Flask 请求只负责接收、登记和返回任务编号，不在请求线程中执行 Spark 计算。
- Spark 结果直接写入 `$HDFS_FEATURE_PATH/ads/<task_id>/`，Flask 使用 Python HDFS 客户端读取聚合结果并转换为 JSON。
- Flask 不把完整原始文件落到本地磁盘，也不把完整居民明细一次性读入内存。
- `DATA_MODE=local` 仅用于 Windows 本地开发、单元测试和小样例；HDFS/Spark 链路必须在对应 Linux 环境完成集成验收。

### 2.3 元数据库

- 使用原生 SQL + DAO，业务服务不直接拼接 SQL，也不直接依赖具体数据库驱动。
- 开发模式使用 SQLite，数据库位置为项目相对路径 `data/localstorage/app.db`。
- 部署模式通过 `get_db_conn()` 切换到 MySQL，业务层不需要改动。
- SQLite 数据库、上传临时状态、运行日志和模型产物不提交 Git。

### 2.4 趋势分析

- 不实现 ARIMA、LSTM 等复杂时序预测。
- 采用多个历史数据集的快照对比。
- 机构上传数据时必须填写 `data_period`，例如 `2026-01` 或 `2026-Q1`。
- 前端展示不同批次的心脏高风险率、卒中高风险率、危险因素率和覆盖人数折线图。
- 快照图表示数据批次之间的统计变化，不直接宣称“干预造成了风险下降”。

### 2.5 辅助模块

- 医疗建议采用本地 JSON 结构化规则知识库，不引入向量数据库。
- 本阶段不接入 LLM，不把居民数据发送到任何公网模型。
- 前端本地部署 ECharts、Bootstrap、词云插件和成都地图 GeoJSON，网络不可用时核心演示仍可运行。
- 个人敏感数据进行掩码脱敏；社区人数少于 5 人时隐藏具体人数、比例和居民明细。

## 3. 总体数据流

```text
浏览器分片上传
    -> Flask 创建 upload_session
    -> 分片写入 HDFS raw 临时目录
    -> 完成校验、合并并登记 dataset
    -> SQLite/MySQL 记录 task 和 dataset
    -> 后台线程提交 Spark 作业
    -> Spark 清洗、区域聚合、批量评分、快照指标
    -> HDFS feature/ads/<task_id>/ 输出结果
    -> Flask HDFS DAO 读取聚合结果
    -> 前端轮询任务状态并展示地图、统计图、名单和趋势
```

Spark 负责大文件数据处理和聚合，模型服务负责统一的特征契约、双模型预测、What-if 和解释逻辑。不得在控制器中写 Spark 计算、模型加载或 SQL。

## 4. 对外接口契约

所有接口保持项目统一响应格式：

```json
{
  "success": true,
  "message": "操作说明",
  "data": {}
}
```

### 4.1 分片上传

| 方法 | 路径 | 用途 |
| --- | --- | --- |
| POST | `/api/uploads/init` | 创建上传会话，登记文件名、大小、分片数、哈希和数据周期 |
| PUT | `/api/uploads/<upload_id>/chunks/<chunk_index>` | 上传一个二进制分片，支持重复提交 |
| GET | `/api/uploads/<upload_id>` | 查询已接收分片和断点续传信息 |
| POST | `/api/uploads/<upload_id>/complete` | 校验分片、合并 HDFS 文件并创建数据集和分析任务 |
| GET | `/api/datasets/<dataset_id>/preview` | 返回有限行数的脱敏预览和字段识别结果 |
| POST | `/api/datasets/<dataset_id>/analyze` | 对已完成的数据集创建分析任务 |
| GET | `/api/task/status/<task_id>` | 返回任务状态、进度、当前阶段、错误信息和结果路径摘要 |
| GET | `/api/datasets/<dataset_id>/result` | 读取已完成任务的聚合结果 |

`/api/task/status/<task_id>` 是前端轮询接口。状态至少包括 `queued`、`running`、`success`、`failed`、`cancelled`，并返回 `progress`、`stage`、`created_at`、`started_at` 和 `finished_at`。

### 4.2 批量评估和 What-if

批量评估与群体统计分开：

| 方法 | 路径 | 用途 |
| --- | --- | --- |
| POST | `/api/risk/batch` | 对已通过字段校验的数据集执行逐行双模型评分 |
| GET | `/api/risk/batch/<task_id>` | 查询批量评分结果状态和导出摘要 |
| POST | `/api/risk/what-if` | 返回基线样本与情景样本的双模型概率变化 |

现有 `/api/analysis/follow-ups` 是基于成都仿真数据标签和筛选规则生成的名单，不是逐人模型概率结果。阶段二不得把该名单改名为模型预测名单；需要逐人概率时必须使用独立的批量评估任务，并在结果中注明模型版本和评分时间。

What-if 请求必须携带基线样本和允许修改的字段。返回值至少包括两组心脏概率、两组卒中概率、变化量、风险等级变化和模型版本。系统必须明确提示这是模型情景模拟，不是医学因果结论。

### 4.3 快照趋势

| 方法 | 路径 | 用途 |
| --- | --- | --- |
| GET | `/api/trends/snapshots` | 按区域、数据周期和模型版本读取历史快照指标 |
| GET | `/api/trends/compare` | 返回多个批次的折线图数据和比较条件 |

只有数据周期、区域口径、特征版本和模型版本一致时，才允许放入同一条趋势线。

## 5. 阶段二任务清单

### P0：阶段一基线和接口契约

**任务内容**：确认 `chenquan` 分支可以启动、预测、读取机构数据并通过现有测试；补充第二阶段接口样例和错误码。

**技术要求**：

- 先运行现有测试，不以缓存文件代替源码。
- 保留两个独立模型和现有特征列。
- 更新 `docs/api_design.md`，使接口文档和实际路由一致。
- 新增接口先提供请求、成功响应、失败响应和空数据样例，再开始前后端并行开发。

**验收结果**：测试通过，页面可以打开，模型未就绪和数据不存在时有明确响应，组员可以按统一 JSON 契约开发。

### P1：上传会话和 HDFS 数据流

**任务内容**：实现分片上传、断点续传、合并校验、HDFS raw 登记和数据集元数据保存。

**技术要求**：

- 使用 `upload_id` 和 `dataset_id`，不能使用用户原始文件名作为路径。
- 分片可以乱序到达，重复分片应幂等，缺失分片不能完成上传。
- 使用 SHA256 校验最终文件，大小和分片数必须一致。
- 分片临时目录位于 HDFS，合并过程采用流式方式，不能把完整文件读入 Flask 内存。
- HDFS 不可用、权限不足、哈希不一致时任务进入失败状态，并保留可定位的错误码。
- 本地开发模式允许使用项目相对临时目录模拟上传，但必须和 HDFS 实现使用同一套服务接口。

**验收结果**：能上传大文件、断点续传、模拟网络中断后继续上传，最终 HDFS 路径和数据库记录一致。

### P1：任务与数据集元数据库

**任务内容**：实现 SQLite/MySQL 可切换的 DAO 和任务状态持久化。

**核心表**：

`datasets` 至少包含：`dataset_id`、`filename`、`file_size`、`file_sha256`、`hdfs_path`、`data_period`、`region_level`、`region_name`、`row_count`、`validation_status`、`upload_time`。

`tasks` 至少包含：`task_id`、`dataset_id`、`status`、`progress`、`stage`、`start_time`、`finish_time`、`error_code`、`error_message`、`spark_app_id`、`result_path`。

必要时增加 `upload_sessions` 和 `snapshot_metrics`，但新增表必须先在文档中说明用途、索引和清理策略。

**技术要求**：

- 所有 SQL 使用参数绑定。
- 每个后台线程独立获取和关闭数据库连接。
- SQLite 和 MySQL 使用同一套 DAO 方法和返回字段。
- 任务状态更新必须具备幂等性，服务重启后不能把已完成任务误改为运行中。

**验收结果**：切换数据库驱动不修改业务服务；任务状态可被前端查询；失败任务保存明确原因。

### P1：CSV 字段校验和数据质量

**任务内容**：对上传数据进行格式、字段、范围、缺失、重复和区域层级检查。

**必需或可选字段**：

- 基本群体分析至少需要年龄、BMI 和一个区域字段。
- 危险因素分析建议包含高血压、糖尿病、胆固醇、吸烟、饮酒和运动字段。
- 机构上传数据按真实使用场景默认不包含疾病标签；只要正式模型可用，机构风险率、区域风险率和随访名单必须使用双模型概率计算。上传文件即使意外包含 `label_heart` 和 `label_stroke`，运行时也不得用标签替代模型结果；标签仅可用于离线校验。
- 批量预测必须具备阶段一模型的 9 个特征，不能用群体聚合列替代模型特征。

**技术要求**：

- 第一版只允许 CSV，编码、分隔符和大小限制通过配置项控制。
- 字段别名映射必须显式记录，不能静默猜错字段。
- 返回总行数、有效行数、无效行数、缺失率、异常示例和字段映射。
- 预览只返回有限行并完成脱敏，不能返回完整原始文件。

**验收结果**：字段缺失、类型错误、范围错误、空文件、重复分片和损坏 CSV 都能返回可理解的错误。

### P1：Spark 清洗、区域聚合和 ADS 结果

**任务内容**：后台线程提交 Spark 作业，完成原始数据读取、质量过滤、双模型批量评分、区域聚合和结果落盘。

**建议输出**：

- `quality_report.json`
- `population_summary.csv`
- `region_summary.csv`
- `risk_factor_summary.csv`
- `snapshot_summary.csv`
- 可选的脱敏 `individual_risk_scores.csv`

所有结果写入 `$HDFS_FEATURE_PATH/ads/<task_id>/`。Flask 默认只读取汇总结果，不将居民明细直接返回浏览器。

**模型执行要求**：

- Spark 任务使用统一的 9 个特征顺序和统一模型版本。
- 可使用 Spark 的 `mapInPandas` 或等价批量方式调用双模型，避免逐行启动 Python 进程。
- 模型文件和校准器必须能被 Spark 执行节点读取或广播。
- 不得在 Spark 任务中偷偷重新训练模型。
- 若当前模型不能安全地在 Spark 执行节点加载，必须先完成兼容性验证，不能用未经验证的结果替代正式评分。

### P1：动态区域地图和机构端页面

**任务内容**：根据后端返回的覆盖范围动态选择地图、排名表或普通图表。

**区域规则**：

- 多个成都区县：显示成都区县 GeoJSON 地图。
- 只有一个区县：显示社区排名、人数和危险因素图，不显示完整成都地图。
- 多城市或多省份：只有存在对应本地边界资源时才显示地图。
- 没有边界资源或区域字段不完整：降级为排名表和柱状图。

**技术要求**：

- 后端返回 `coverage_level`、`coverage_name`、`map_name`、`map_available` 和区域聚合数据。
- 成都地图资源放在 `static/geo/`，不依赖外部 CDN 或远程 GeoJSON。
- 地图颜色表示区域聚合指标，只能用于区域之间比较，不称为个人发病概率。
- 页面必须处理空结果、任务失败、地图资源缺失和网络断开。

### P1：多次快照对比

**任务内容**：机构上传多个时间段的数据集，前端展示心脏和卒中高风险率、危险因素率和覆盖人数变化。

**技术要求**：

- 每个数据集必须填写 `data_period`。
- 同一趋势图的区域层级、指标定义、模型版本和特征版本必须一致。
- 分母变化、区域覆盖变化和缺失标签必须在结果中提示。
- 对没有标签的数据只能展示危险因素快照，不能伪造疾病高风险率。
- 不能把快照变化直接写成因果结论。

### P1：What-if 情景模拟

**任务内容**：在 C 端对 BMI、吸烟、运动、高血压等允许字段进行情景修改，分别调用心脏模型和卒中模型计算基线与情景结果。

**技术要求**：

- 基线输入和情景输入都必须通过同一套校验和特征工程。
- 只允许修改白名单字段，保持性别、年龄等不可变字段的约束。
- 返回两个模型各自的基线概率、情景概率、变化量和风险等级变化。
- 页面文案使用“模型情景结果”，不能使用“必然降低”或“治疗效果确定”等表述。

### P1：SHAP 和模型解释优化

**任务内容**：保留现有 SHAP 初版，优化模型加载缓存、解释器缓存、版本兼容和异常降级。

**技术要求**：

- 心脏和卒中分开解释，不把两种疾病的贡献混成一个医学结论。
- 贡献值表示相对模型输出的解释，不直接等同于概率变化。
- SHAP 不可用时预测接口仍必须正常返回。
- 增加全局特征重要性和个人局部解释的区分。
- 本阶段不再额外引入 LIME，避免重复建设。

### P2：候选模型比较和 Stacking

**任务内容**：离线比较 Logistic Regression、Random Forest、GBDT/HistGradientBoosting，必要时构建每个目标独立的 Stacking 候选模型。

**技术要求**：

- 心脏和卒中分别评估，不能合并为一个多分类实验。
- 测试集保持自然患病率，不能用过采样测试集计算最终指标。
- 至少比较 ROC-AUC、PR-AUC、Recall、Precision、F1、F2、Brier Score 和校准曲线。
- Stacking 使用训练集外预测，防止元模型看到泄漏信息。
- 候选模型先写入评估报告，不直接替换正式模型。
- 只有指标、校准、阈值和资源消耗都满足验收标准，才提交模型发布申请。

### P2：本地 JSON 医疗规则知识库

**任务内容**：将现有固定建议整理成可审核、可版本化的本地知识库，使用规则匹配检索，不引入向量数据库和 LLM。

**建议位置**：`resources/knowledge/intervention_rules.json`。该目录属于共享代码资源，不放入含居民数据的 `data/` 目录。

**单条规则至少包含**：`rule_id`、`factor`、`risk_levels`、`disease_scope`、`advice`、`source`、`version`、`review_date`、`contraindication`。

**技术要求**：

- 规则优先级明确，重复建议去重。
- 无匹配规则时回退到固定通用模板。
- API 返回建议来源和知识库版本。
- 不输出药物剂量、诊断结论或未经审核的个性化医疗方案。
- 规则内容变更必须经过组内审核并记录变更说明。

### P2：隐私、安全和匿名化

**任务内容**：为机构上传、任务查询、结果展示和随访名单增加基本安全边界。

**技术要求**：

- 上传文件使用应用生成的安全文件名和限定目录。
- 不能信任浏览器提交的文件名和 MIME 类型。
- 限制文件大小、分片大小、并发上传数和任务查询频率。
- 社区人数小于 5 人时隐藏数量、比例和明细。
- 对居民编号、姓名、联系方式等字段进行掩码或禁止回传。
- 对外联网部署至少增加身份认证、角色权限、HTTPS 和操作审计。

### P2：性能、离线能力和可观测性

**任务内容**：保证 200 万级数据和断网答辩场景下可用。

**技术要求**：

- 页面本地加载 ECharts、Bootstrap、词云插件和成都 GeoJSON，并保留版本和许可证说明。
- 本地群体分析使用分块读取，HDFS 模式使用 Spark，不使用无边界的 `toPandas()`。
- 模型、SHAP 解释器和静态地图资源使用缓存。
- 任务日志记录任务编号、数据集编号、Spark 应用编号、阶段、耗时和错误码。

## 6. 验收测试矩阵

### 上传与任务

- 分片乱序、重复、缺失、断点续传和哈希错误。
- HDFS 不可用、权限不足、Spark 提交失败和任务线程异常。
- 服务重启后任务状态可恢复，已完成任务不会重复计算。

### 数据与分析

- 成都全区县数据显示区县地图。
- 单一区县数据降级为社区排名。
- 没有标签时不展示疾病高风险率。
- 社区人数小于 5 人时完成匿名化。
- 多个 `data_period` 可以生成一致的快照折线图。

### 模型与 C 端

- 双模型同时返回心脏和卒中概率。
- What-if 返回基线、情景和变化量。
- SHAP 缺失或解释失败时不影响预测。
- 候选模型不覆盖 active 模型。

### 运行与前端

- 无网络时页面、ECharts、成都地图和核心接口仍可用。
- API 错误、空数据和任务失败均有明确页面状态。
- Windows 本地模式和 Linux HDFS/Spark 模式分别完成对应测试。

## 7. 训练和耗时说明

地图、上传、质量检查、快照聚合、What-if 和 RAG 规则检索不需要重新训练模型。

模型对比和 Stacking 只允许离线执行。以当前 DWD 数据规模为基准，双模型已有训练耗时约为 1 分钟量级；新增模型比较预计需要数分钟，带交叉验证的 Stacking 预计需要十几到几十分钟，具体以训练估算接口和实际硬件为准。未经组长审核不得覆盖模型清单，不得把模型文件和训练产物提交 Git。

## 8. 阶段二完成标准

阶段二不以“功能页面能打开”为完成标准，必须同时满足：

1. API、数据库、HDFS 路径和 Spark 输出字段有明确契约。
2. 大文件处理不阻塞 Flask 请求，任务状态可追踪。
3. 上传数据不会覆盖正式模型或泄露居民明细。
4. 地图随数据覆盖范围变化，单区域数据可以正确降级。
5. 趋势图只做有数据依据的快照比较。
6. RAG 使用可审核的本地规则，LLM 不进入本阶段运行链路。
7. 所有成员提交自己的测试和交付说明，组长完成集成验收后才允许进入 `main`。
