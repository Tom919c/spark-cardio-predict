# Opus 4.8 项目审核提示词

以下内容请整体复制给 Opus 4.8 使用。请让 Opus 在当前项目工作区中进行审核，不要脱离代码和文档凭经验臆测。

```text
你现在是本项目的高级技术架构师、机器学习工程师和全栈代码审查专家。请对当前工作区中的“基于 Spark 的心脑血管疾病风险预测与分析系统”进行一次系统性审核。

你的任务不是直接修改代码，而是基于当前仓库真实文件、运行结果和文档，判断项目目前是否真正达到设计目标，并提出可以落地的具体改进建议。除非我后续明确要求，否则不要创建、删除、覆盖或修改任何项目文件，不要提交 Git，不要推送远程仓库。

一、审核前必须完成的工作

1. 先阅读并理解以下文档：

   - `mydocs/项目方案.md`
   - `mydocs/成都居民健康数据.md`
   - `docs/phase2_task_plan.md`
   - `docs/phase2_team_division.md`
   - `docs/architecture.md`
   - `docs/api_design.md`
   - `docs/data_dictionary.md`
   - `docs/test_guide.md`
   - `docs/training_results.md`
   - `README.md`

2. 再阅读实际代码，重点包括：

   - Flask 应用入口和路由注册
   - `src/controllers/`
   - `src/services/`
   - `src/dao/`
   - `src/ml/`
   - `src/spark_jobs/`
   - `scripts/`
   - `templates/`
   - `static/`
   - `resources/knowledge/`
   - `tests/`

3. 检查当前 Git 状态、当前分支、最近提交和项目依赖，但不要修改 Git 状态。

4. 尽可能运行只读检查和测试，例如：

   - 运行现有自动化测试
   - 检查 Flask 路由是否真实存在
   - 检查接口返回字段是否与文档一致
   - 检查 Python 文件语法
   - 检查前端 JavaScript 语法
   - 检查模型清单和模型文件是否匹配
   - 检查本地模式和 HDFS/Spark 模式的配置链路

如果某项无法运行，必须说明具体原因，不要把“没有运行”写成“功能不存在”。

二、项目当前已确认的设计目标

1. 这是一个心脑血管疾病风险预测与分析系统，包含两个使用场景：

   - 个人端：个人输入健康因素，获取心脏事件和脑卒中风险评估、风险等级、解释信息和健康建议。
   - 机构端：机构上传居民群体数据，系统分析区域、年龄、危险因素和模型高风险情况，并支持多个时间快照趋势比较。

2. 模型采用两个独立的二分类模型：

   - 模型 A 预测心脏事件。
   - 模型 B 预测脑卒中。
   - 两个模型分别输出概率，不允许把它们改成互斥多分类逻辑。
   - 概率经过保序回归校准。
   - 风险概率是模型输出，不是临床诊断，也不是干预产生的因果结果。

3. 当前实际模型可能已经从原设计中的随机森林调整为 XGBoost。请重点核对：

   - 设计文档、训练代码、模型清单、模型文件、预测服务是否一致。
   - 如果发现文档写的是随机森林而实际 active model 是 XGBoost，请明确指出这是“代码与文档不一致”，不要简单判断为代码错误。
   - 候选模型、Stacking 和 active model 必须区分，候选模型不得自动覆盖正式模型。

4. 个人模型输入特征目前是：

   - `age`
   - `gender`
   - `bmi`
   - `cholesterol`
   - `diabetes`
   - `hypertension`
   - `smoker`
   - `alcohol`
   - `exercise`

5. 机构真实上传数据通常不包含疾病标签。机构端正式运行时应当：

   - 使用双模型概率进行逐人评分和群体聚合。
   - 不能要求机构提供 `label_heart` 或 `label_stroke` 才能分析。
   - 如果上传文件意外包含标签，标签只能作为离线校验信息，不能覆盖正式模型输出。
   - 前端应明确区分“事件标签率”和“模型高风险率”。

6. 机构上传链路设计为：

   浏览器分片上传
   -> Flask 创建任务
   -> 分片合并
   -> 本地模式或 HDFS raw 数据保存
   -> 后台异步分析
   -> Spark 或本地分块分析
   -> ADS 汇总结果
   -> 前端轮询任务状态并展示结果

7. 机构页面的数据来源必须遵守：

   - 没有成功上传并分析完成的数据时，显示等待上传的初始化状态。
   - 不能自动把训练用的 200 万居民仿真数据当作机构当前数据展示。
   - 上传完成后，当前上传数据应接管整个机构看板，而不只是更新上传卡片。
   - 当前数据集应能追溯到 `dataset_id`、数据文件、数据周期、模型版本和特征版本。

8. 趋势分析不实现 ARIMA 或 LSTM，而是比较多个历史数据集的快照：

   - 每个批次必须有 `data_period`。
   - 只有统计口径、区域层级、模型版本和特征版本一致时才能放在同一条趋势线中。
   - 趋势变化只能描述统计变化，不得直接表述为干预造成的因果效果。

9. 医疗建议模块使用本地 JSON 结构化规则知识库：

   - 本阶段不接入 LLM。
   - 本阶段不使用向量数据库。
   - 规则必须可审核、可追踪版本和来源。
   - 不应输出药物剂量、诊断结论或未经审核的个体化处方。

10. 数据安全要求：

   - 姓名、电话、证件号、居民编号等敏感信息不能直接返回浏览器。
   - 预览数据需要脱敏。
   - 社区人数小于隐私阈值时隐藏人数、比例和居民明细。
   - 上传路径不能信任用户原始文件名。

三、审核范围

请至少从以下方面进行审核。

### 1. 产品目标与需求一致性

判断当前系统是否真的实现了个人端和机构端的核心闭环，重点检查：

   - 页面展示的数据是否来源正确。
   - 页面文字是否与真实数据语义一致。
   - 无数据、加载中、分析中、分析成功、分析失败、模型未就绪时是否有清晰状态。
   - 页面是否存在静态假数据、旧数据残留或重复数据源。

### 2. 系统架构

审核 Flask、服务层、DAO、机器学习模块、Spark 作业和前端之间是否真正解耦，重点检查：

   - 控制器是否直接写 SQL、加载模型或编写 Spark 计算。
   - 业务层是否依赖具体数据库驱动。
   - 本地模式和 HDFS/Spark 模式是否拥有一致的结果契约。
   - 上传请求是否会被耗时分析阻塞。
   - 服务重启后任务状态是否可能丢失或卡死。

### 3. 机构上传与当前数据接管

必须重点追踪完整链路：

   - 上传初始化
   - 分片上传
   - 乱序分片
   - 重复分片
   - 分片合并
   - 文件校验
   - 数据集登记
   - 异步任务创建
   - 任务状态轮询
   - 分析结果落盘
   - 当前看板读取
   - 前端全页面刷新

请明确回答：

   - 当前页面无上传数据时是否会展示默认训练数据。
   - 上传成功后哪些组件真正使用了新数据，哪些组件仍然使用旧接口或旧缓存。
   - 多次上传后系统如何决定当前数据集。
   - 上传失败后是否会错误地覆盖原来的成功结果。

### 4. 模型与数据科学质量

审核：

   - 双模型是否真正独立运行。
   - 模型概率、预测标签和五级风险之间是否存在阈值混用。
   - Isotonic 校准是否只使用训练/校准集，测试集是否保持自然患病率。
   - 卒中不平衡处理是否错误地污染了测试集。
   - 机构端无标签数据是否真正使用模型概率。
   - SHAP 或模型解释失败时预测接口是否仍然可用。
   - What-if 是否被错误描述成因果结论。
   - 训练数据是仿真数据还是临床真实数据，是否在页面和文档中明确说明。

### 5. 数据生成与演示数据

审核仿真数据是否存在以下问题：

   - 年龄单一决定高危。
   - 危险因素之间完全独立，没有多因素聚集。
   - 各区域风险颜色完全一致。
   - 多月快照只是重新随机生成的不同人群，而不是同一居民面板。
   - 姓名、联系电话和区域字段不真实或无法脱敏。
   - 生理指标之间不符合基本关系，例如 BMI、身高、体重和血压互相矛盾。

请给出数据生成规则方面的具体改进建议，并区分“为了答辩演示可接受”和“医学上不能这样解释”的部分。

### 6. Spark/HDFS 集成

审核：

   - HDFS raw、staging、feature、ADS 路径是否一致。
   - Spark 是否真正执行大文件读取、聚合和批量模型评分。
   - Spark worker 是否能加载模型、自定义源码和依赖。
   - 是否存在无边界 `toPandas()`、逐行启动进程或将居民明细全部收集到 Driver 的问题。
   - Spark 输出是否与本地模式的 JSON 契约一致。
   - HDFS 不可用、Spark 提交失败、权限不足时，任务是否会记录可定位的错误。
   - 不要因为仓库里存在 Spark 脚本就认定 HDFS/Spark 链路已验收，必须看测试或运行证据。

### 7. 数据库、任务状态与幂等性

审核 SQLite 和 MySQL DAO 是否具有相同方法契约，重点检查：

   - SQL 是否全部参数化。
   - 后台线程是否独立获取和关闭数据库连接。
   - 任务状态是否允许非法跳转。
   - 重复 finalize、重复 submit、重复分片是否幂等。
   - 已完成任务是否可能被服务重启重新改为运行中。
   - 数据集和任务之间是否能正确关联。

### 8. 隐私与安全

检查：

   - 文件名、路径、MIME、大小、分片数量是否经过服务端校验。
   - 是否有路径穿越、任意文件覆盖、过大文件、异常 CSV 和恶意内容风险。
   - API 是否存在越权查看其他任务或数据集的可能。
   - 个人信息是否在日志、错误信息、前端表格或 JSON 中泄露。
   - 小样本匿名化是否覆盖区域图、汇总、趋势和随访名单。
   - 如果联网部署，身份认证、角色权限、HTTPS 和审计是否缺失。

### 9. 前端体验与视觉实现

只审核和建议前端渲染，不要求改变后端功能。检查：

   - 机构端是否存在清晰的初始化空状态。
   - 上传中、分析中、失败、成功状态是否容易理解。
   - 图表是否与数据源语义一致。
   - 地图在全成都、多区县、单区县、社区和无地图资源时是否正确降级。
   - 个人端风险仪表盘、结果卡片、解释模块是否层次清晰。
   - 是否存在过度渐变、无意义装饰、颜色混乱、卡片堆叠、文字过小或移动端溢出。
   - 页面是否保留现有路由、字段名、接口行为和操作流程。
   - 是否尊重 `prefers-reduced-motion`，并保证按钮、输入框和图表文字的对比度。

四、审核方法要求

1. 所有结论必须尽量附证据：文件路径、函数名、接口路径、代码行号、测试名称或实际命令输出。

2. 区分以下四种情况，不要混写：

   - 已实现且有测试或运行证据。
   - 代码存在但没有真实集成证据。
   - 部分实现，存在边界条件或口径不一致。
   - 完全未实现。

3. 不要只根据测试通过就判断项目完整。测试覆盖不到的地方必须明确标记为“未验证”。

4. 不要把设计文档当作当前事实。代码、运行结果、数据库记录和模型清单优先级更高；如果代码和文档冲突，请同时指出冲突双方。

5. 不要建议为了通过测试而伪造指标、补写静态结果、隐藏错误或绕过数据校验。

6. 对风险进行分级：

   - P0：会导致核心功能错误、数据错用、隐私泄露、模型结果失真或演示无法完成。
   - P1：主要功能可以运行，但存在明显错误、数据口径问题、兼容问题或较大维护风险。
   - P2：体验、可维护性、性能、文档或测试完善项。

五、最终输出格式

请使用中文输出一份结构化审核报告，必须包含以下章节：

### 1. 一句话结论

说明当前系统处于什么状态，例如“本地演示闭环基本可用，但分布式集成和接口契约仍未完成验收”。不要只写“总体不错”。

### 2. 当前系统真实架构

用简短文字或 Mermaid 图描述真实的数据流：个人端、机构端、上传、任务、数据库、本地分析、Spark/HDFS、模型和前端之间如何连接。

### 3. 按模块审核结果

使用表格：

| 模块 | 状态 | 证据 | 主要问题 | 优先级 |
|---|---|---|---|---|

### 4. P0/P1/P2 问题清单

每个问题必须包括：

   - 问题标题
   - 严重级别
   - 具体证据
   - 影响
   - 推荐修复方案
   - 建议修改的文件或模块
   - 验证方式

### 5. 设计文档与代码不一致项

单独列出文档说法、代码实际行为和建议统一方向。

### 6. 机构端专项结论

必须回答：

   - 无上传数据是否有正确初始化状态。
   - 新上传数据是否能接管完整看板。
   - 页面是否还可能读到默认 200 万居民数据。
   - 多月快照趋势是否使用同一统计口径。
   - 无标签机构数据是否使用模型概率。

### 7. 模型与医学安全结论

明确哪些内容只能用于风险筛查演示，不能表述为临床诊断或因果干预结论。

### 8. 建议的最小修复顺序

给出不超过 10 项的实施顺序，每项写清楚预期交付结果。优先保证数据来源正确、核心闭环正确和安全边界正确。

### 9. 审核后仍需人工验证的项目

列出必须由项目组在真实 Windows、WSL2 或 VMware 环境中验证的内容，包括 Spark、HDFS、模型依赖、浏览器行为和断网演示。

六、重要边界

   - 不要直接改代码。
   - 不要自动安装依赖。
   - 不要删除数据库、模型、数据或上传文件。
   - 不要提交 Git 或推送远程仓库。
   - 不要将本地绝对路径、个人环境名称或个人账号写进建议文档。
   - 不要凭空添加 LLM、RAG 向量库、ARIMA、LSTM 或其他没有进入当前阶段方案的技术。
   - 不要把模拟数据性能写成真实临床性能。
   - 不要把模型概率写成发病确定性或治疗效果。

请先完成仓库和文档阅读，再输出完整审核报告。审核报告要以当前代码和可验证证据为准，重点指出具体问题和可以直接执行的改进方案。
```

## 使用说明

将上面的代码块完整复制给 Opus 4.8，并让它在项目仓库根目录工作。建议同时要求它先只读审核，不要直接修改代码。拿到审核报告后，再由项目负责人根据 P0、P1、P2 优先级决定哪些建议进入下一轮开发。
